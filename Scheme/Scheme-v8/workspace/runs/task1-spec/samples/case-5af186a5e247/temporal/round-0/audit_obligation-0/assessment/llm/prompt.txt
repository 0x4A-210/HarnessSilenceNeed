[D1] Target: one fuzz entry point with its helpers and build recipe. The OLD harness is fixed; the new harness is unavailable and must not be imagined.
[D2] Operational surface: the entry's primary operations plus the objects, input formats/protocols, configuration and state they take. [D3] Obligation: a tuple <operation, condition, capability, consequence> that the target must satisfy to keep its operational surface under the changed source.
[D4] Execution-compatibility obligation: the target builds, initializes, invokes its operations, keeps valid lifetime/state, and every EXISTING harness assertion/check stays true for inputs the source accepts.
[D5] Target-coverage obligation: a behavior the source contract supports inside the target's operational surface must be reachable by the target with a valid input and a supported setup/state. [D6] Static environment: the supplied build recipe and repository defaults fix configuration and platform. Behavior unreachable under them is out of scope. Do not invent compiler flags, input bounds, successful builds or execution results; read delegated configuration when it is decisive.
[D7] Out of scope (not obligations): (a) new or stronger assertions absent from the harness; (b) internal implementation paths that the supported contract does not distinguish, e.g. visiting one more internal branch; (c) APIs, tools or fuzz targets outside the operational surface; (d) successful processing of invalid inputs that the source safely rejects; (e) an alternative spelling that reaches the same implementation.
[D8] Equivalent route: the obligation is satisfied if natural inputs, defaults, aliases, delegated helpers or another call sequence of the target already exercise the behavior.
[D9] Input model: the bytes the fuzzer supplies to the entry, under the static environment (D6). The runtime environment (allocator, file system, clock, other processes) behaves normally unless the target itself makes it depend on the input; a witness that requires such an environment failure is not feasible.
[J1] needs_update requires at least one obligation whose five premises are each supported by source AND harness evidence: (a) scope_contract: it belongs to the operational surface (D2); (b) feasible_trigger: a finite witness input/state/configuration exists under the input model (D9); (c) observable_consequence: an execution failure or invalid EXISTING assertion (D4), or a specific supported behavior that cannot be reached (D5); (d) alternatives_ruled_out: no equivalent route (D8); (e) identity_preserved: the same tuple is assessed throughout.
[J2] Maintenance does not require that this change introduced the problem; a preexisting failure that still blocks the target counts.
[J3] One established obligation suffices for needs_update; uncertainty elsewhere does not veto it.
[J4] satisfied_in_scope requires every change group assessed as covered or not_target_relevant with evidence, the four foundations (build, input, lifecycle, control_flow) assessed as pass or not_applicable with evidence, and no pending decisive evidence. [T1] Timing assesses the SAME obligation tuple on the before and after source against the SAME old harness.
[T2] introduced: unsatisfied after, and not required or satisfied before. preexisting: required and unsatisfied before with the same blocker.
