# 提示词规则审计（v7 → v8）

审计对象：v7 默认流程（`obligation_ledger_dual` + `split_coverage_compatibility`）实际发送给模型的全部提示词文字，另加一处确定性启发式规则。

**分类：**
- **定义**：能由问题定义直接推出，保留，或改写为 `docs/判定规格.md` 中的条款。
- **协议**：只说明输入、输出字段或引用方式，不含判定，保留。
- **特化**：只是某个样本的具体化，删除；如果背后有一般原则，就并入对应条款。
- **不明**：说不清来源，默认删除。

**提示词组成（v7）：**
- 维护：`maintenance.PROMPT` + `target_contract` 追加指导 + `retrieval.COMMON_RULES` + `BATCH_RULES` + `LOCATION_RULES` + `policy.POLICY` + `ledger_rules`
- 时间：`prompts/independent.txt` + `COMMON_RULES` + 时间追加段 + 同上
- 必要性闸门：`policy.GATE_PROMPT`（内含 `policy.POLICY`）
- 其余：`FACT_PROMPT`、`REGISTRY_PROMPT`、引用修复 `REPAIR_PROMPT`、`LOCATION_RULES`、`DIFF_RULES`、范围审查任务句

`IMPACT_PROMPT`、`necessity_proof.POLICY`、`LEDGER_RULES` 在 v7 默认流程中不发送给模型（只参与协议哈希）。v8 同样把它们改为由规格生成，避免代码里残留特化文字。

## 冒烟测试后的补充

用 V3-22 做冒烟测试时，模型以“某次 `malloc` 返回 NULL”为见证判出泄漏，并通过了必要性闸门。原因是 J1(b) 引用了“输入模型”，但规格没有定义它；v7 中的特化规则 CR10（“推测性分配失败不够”）实际上替这个缺失的定义打了补丁。

处理：新增一般性定义 **D9 输入模型**（fuzzer 送入的字节 + 静态环境；运行环境按正常行为处理，除非目标让它依赖输入），J1(b) 改为引用 D9。D9 不提及任何样本，但它是在看到一条开发集样本的中间输出后补的，在此如实记录。全量运行在这次补充之后进行，之后不再修改提示词。

## 规格修订（2026-11-06）：隐式缺口改为“变更的可执行性”

**动机：** task3 的错误分析显示，6 条误报全部是“库支持、但 harness 没用到的选项 / 模式”被当成了覆盖缺口；而 V3-12 这样“变更代码被构建配置编译掉”的阳性，又被 D6 判为不在范围内。数据集的操作定义（`dataset.json` 的 conventions）是：阴性要求改动的行被语料覆盖、且没有新崩溃；隐式阳性要求缺口所在的行 / 分支覆盖为 0、修复后被覆盖；显式阳性指构建失败或崩溃，与变更是否相关无关。

**修改：**
- **D5** 的对象由“操作面内所有受支持的行为”改为“本次变更的代码或行为能否被目标执行到”；
- **D6** 只把平台和工具链当作固定环境，harness 的构建配方属于目标、可能过时；
- **D7(f)**：变更代码已经能被执行到时，没用到的其他选项不算缺口（补回审计时合并 P17 而丢失的原则）；
- **J1(a)(c)** 和 **J4** 随之修改。

**说明：**
- 这次修订与数据集的标注口径对齐，没有引用任何具体样本。但它是在看过开发集的错误之后做出的，属于对开发集的又一次调整，测试集上的结论必须单独验证。
- “变更所在函数中的相邻分支（例如复用分支）是否计入”尚未约定，D5 目前只针对变更新增或改动的代码。

### 补充（2026-11-06）：T2 时间口径
T2 增加“时间判断看的是阻碍本身，而不是被挡住的代码”。D5 改为以变更代码为对象之后，新增代码在修改前当然不存在，时间判断会系统性地偏向 introduced；这与数据集的定义（把修复应用到修改前的版本，同一缺口随之消失，即为原本存在）不一致。这次补充同样是看过开发集错误（V3-10）之后做的。

### 修订（2026-11-06）：两步法覆盖口径；T2 按义务类别区分
- **D5 改为两步法：** 第 1 步看变更的核心行为是否已被执行到；第 2 步，核心行为没被执行到时，看目标是否“本来就应该”通过自身的操作（换一种用法）触达它。只能经由目标未使用的入口或环境故障才能触达的，不算义务。D7(f)、J1(a)(c)、J4 随之修改。
- **T2 撤回此前“看阻碍本身”的补充**（它会把 V3-16 这类“新增行为被旧限制挡住”的情况错判为原本存在）。改为：D4 类义务比较两侧的失败；D5 类义务看执行不到的代码本身是否为本次新增，或者它（及其替换的旧代码）在修改前是否同样执行不到。
- **依据：** 数据集的标注理由和覆盖记录（11 条阴性的变更覆盖率小于 1；12 条隐式阳性的缺口代码与本次新增 / 重写 / 旧代码之间的对应关系）。同样属于看过开发集之后的调整。

### 修订（2026-11-06）：T2 覆盖类义务改看“最内层从未被满足的条件”
D5 类义务的时间判断，改为看真正挡住执行的、最内层那个从未被满足的条件是新增的、原有且同样从未满足的，还是原有但被本次修改变得无法满足的。依据：V3-12 中新代码位于原本就被编译掉的 `#if` 块内，按“看代码是否新增”的规则会产生歧义；这条细化同时与 V3-16、V3-44、V3-10 的标签一致。属于看过开发集之后的调整。
