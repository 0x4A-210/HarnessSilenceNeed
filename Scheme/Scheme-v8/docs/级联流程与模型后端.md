# 级联流程与可替换模型后端

> 2026-11-09 更新。验证记录保留了当时的原始数字。

## 流程（`llm/attribution/cascade.py`，配置 `llm.engine: cascade_session`）

一条样本只开一个会话。通常 2–4 轮，最多 7 轮左右（task4 两次全量的平均为 3.3 次调用）：

| 轮次 | 会话 | 发送内容 | 输出 |
|---|---|---|---|
| 0（程序） | — | 只构建一次证据包，两个判断共用；附带 `program_facts`（构建配置事实） | — |
| 1 发现 | 新会话 | 任务背景 + 规格 + 完整证据包 | 候选义务、范围评估、补读请求 |
| 2 复核 | Claude：从第 1 轮分叉；Codex：续接 | 第 1 轮请求补读的新证据、引用错误、候选清单 | 每个候选的必要性闸门结论、范围审查、`new_candidates` |
| 新候选复核（≤ `cascade_new_candidate_rounds`） | 续接复核会话 | 复核轮提出的新候选 | 这些新候选的闸门结论 |
| 引用修复（`cascade_citation_repair`） | 续接当前会话 | 核验不通过的引用位置 | 只替换这些位置，其余内容冻结 |
| 补读后复核（≤ `cascade_extra_rounds`） | 续接复核会话 | 复核请求补读的新证据 | 对仍为 uncertain 的候选重新复核 |
| 3 时间（只在 `needs_update` 时） | 续接复核会话 | 保留义务所在变更组的修改前 / 后源码，以及义务引用到、但本次没有改动的文件的前后配对（两侧相同） | 逐条义务的前后两侧事实；时间标签由程序推导，必要性冻结 |

- 已发送过的证据单元不再重发；后续轮次不再发送证据目录和 `program_facts`。
- 证据包超过单次请求容量时，拆成多段，最后一段带上任务。
- 程序侧校验全部沿用：引用定位与哈希、五项前提闸门、阴性闭合、时间由两侧事实推导。
- 整个会话使用同一个输出 schema（`SESSION_SCHEMA`）。每段都是“对象或 null”：每轮只填写本轮那一段，其余设为 null。共用一个 schema，是因为 schema 一变，缓存前缀就会失效（见下方验证记录）；用“对象或 null”，是为了从格式上杜绝“返回多项”。本轮那一段为 null 或 `turn` 不对时，追加一次纠正轮。
- 旧的双模块流程保留为 `configs/legacy-dual.yaml`，供消融使用。

## 模型后端（`llm/backends.py`，配置 `llm.provider`）

| provider | 调用方式 | 新会话 | 续接 | 分叉 |
|---|---|---|---|---|
| `codex_cli` | `codex exec`（ChatGPT 登录） | 不加 `--ephemeral` | `codex exec resume <id> -` | 不支持（改为续接） |
| `claude_cli` | `claude -p --output-format json --json-schema`（订阅登录） | 默认持久化 | `--resume <id>` | `--resume <id> --fork-session` |

两者都不走 API key。工具一律关闭：Codex 用 `features.*=false` 加只读沙箱，Claude 用 `--tools ""` 并且不加载任何设置或 MCP。Codex 单次调用的命令与 v7 逐项一致。

失败分类：
- 网络断连、过载、限流：同一次调用最多重试 `transient_retries` 次（默认 3）。
- 账户额度耗尽：抛出 `QuotaExhausted`，runner 停止整批并写 `incomplete.json`，不把它记成 `unknown`。
- 被安全过滤拦截：抛出 `ContentFlagged`，不重试，该样本记为 `unknown`。

v7 原有的 `llm/client.py`、`llm/retry_client.py` 已于 2026-11-09 删除；Codex 的单次调用命令由 `CodexCLI` 生成，与 v7 逐项一致。

切换方式：`--config configs/claude.yaml`（只覆盖 provider、model、effort）。

## 验证计划 1（Claude，2026-11-05）

`tools/verify_sessions.py`，约 4.2 万 token 的固定前缀，三轮调用：

| 设置 | 续接：缓存读取 / 写入 | 分叉：缓存读取 / 写入 | 续接能答出只在首轮出现的事实 |
|---|---|---|---|
| 三轮使用同一 schema | 42,326 / 167 | 42,493 / 170 | 是 |
| 续接时换 schema | **0 / 42,475** | 42,475 / 197 | 是 |

结论：续接和分叉都有效；同一个 schema 才能命中缓存。原始记录在 `reports/verification/`。

端到端单样本（V3-22，阴性，Claude `claude-opus-5-5`，high）：判为 `satisfied_in_scope`，2 次调用，102 秒，输入共 121,617 token（其中 49,366 命中缓存），输出 9,618 token。v7 同一样本为 14 次调用、约 1045 秒、约 125 万输入 token。这只是一条样本，不代表整体效果。

Codex（2026-11-05）：续接时未缓存 251 / 缓存命中 43,520，能答出首轮的事实；不支持分叉。`codex exec resume` 报告的是整个会话的累计用量，由 `CodexCLI.per_turn()` 换算成本轮用量。V3-22 端到端：2 次调用，145 秒，输入 113,890（其中 37,888 命中缓存），输出 6,842，判为 satisfied（正确）。

“对象或 null” schema 的兼容性验证（`tools/verify_nullable.py`，2026-11-05）：Codex 和 Claude 都接受 `anyOf: [object, null]`，并且都只填写指定的那一段（`reports/verification/nullable-*`）。
