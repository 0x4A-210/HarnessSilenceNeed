# 方法论：静态检测 fuzz harness 的维护需求

> 2026-11-09 整理。本文从 scheme-v8 的设计与实验中提炼出一套方法论，可作为论文“方法”一节的底稿。
> 文中的实验数字都来自开发集 Dataset-v8（48 条），尚未在独立测试集上验证。实现细节见 `方案说明.md`，条款全文见 `docs/判定规格.md`，实验记录见 `docs/运行状态.md`。

## 0. 一句话概括

> **把“harness 是否需要维护”定义成一组可证伪的义务；由模型在规格约束下做语义判断，由程序负责证据的真实性和结论的汇总；用一个增量的会话流程完成，并用与动态实测口径对齐的定义来评测。**

方法分为四层：

| 层次 | 回答的问题 | 包含的原则 |
|---|---|---|
| 问题抽象 | “需要维护”怎样变成可判定的问题 | P1 义务化、P2 两步法覆盖口径、P3 时间归因 |
| 判断方法 | 模型和程序各自负责什么 | P4 规格驱动、P5 模型提出 + 程序核验、P6 不对称的三值判定 |
| 工程落地 | 怎样既拿到关键证据，又足够快 | P7 确定性补证据、P8 增量会话与缓存稳定 |
| 评测方法 | 结论怎样才可信 | P9 口径对齐、P10 重复运行与技术失败分离、P11 开发集纪律 |

## 第一层：问题抽象

### P1 维护需求 = 一条未被满足、且有证据支持的义务

**做法**
- 义务是四元组 ⟨操作, 条件, 能力, 后果⟩，分为两类：
  - **运行兼容性**（D4）：目标能否构建、初始化、调用自身的操作，已有断言是否仍然成立；
  - **目标覆盖**（D5）：该触达的行为能否被触达（见 P2）。
- 判阳需要至少一条义务的**五项前提**都有源码和 harness 的证据支持（J1）：
  - 范围契约：义务属于目标的操作面；
  - 可行触发：在输入模型下存在有限的见证；
  - 可观察后果：执行失败、已有断言失效，或核心行为执行不到；
  - 排除替代：不存在等价路径；
  - 身份保持：评估始终针对同一个四元组。
- 不要求问题由本次变更引入（J2）。

**为什么**
- “harness 是否过时”本身是个模糊问题，模型容易泛泛而谈。拆成义务后，每个结论都对应一个具体、可反驳的主张，可以逐条核验，也可以逐条消融。
- 五项前提把“看起来有问题”和“有证据证明有问题”区分开来。

**证据**：v7 没有边界的口径（“受支持的行为都应可触达”）带来 34.8% 的误报率；收紧到义务加五项前提，并配合 P2 之后，误报率降到约 15%（两次全量平均 14.6%）。

### P2 覆盖缺口的定义：两步法，“harness 本来就应该触达的”

**做法**（D5、D6、D7(f)）
- **对象**：变更的**核心行为**，即这次变更所针对的机制，例如新的检查、状态处理、格式分支、错误通道；如果是重写，就是重写后的行为。
- **第 1 步**：存在有效输入，在目标的构建配方和调用方式下执行到了核心行为 → 不构成覆盖义务，即使变更的其他部分没被执行到。
- **第 2 步**：核心行为没被执行到时，如果能通过**目标自身的操作换一种用法**触达，就构成义务。“换一种用法”包括：对同一对象多次调用或续用、同一调用的其他选项或标志、仓库提供的编译开关、同一入口的另一种输入形式、修掉挡住它的 harness 缺陷。
- 只能经由目标**没有使用的入口**才能触达，或者只能靠**环境故障**触发的，不算义务。
- **构建配方属于目标，可能已经过时**：被它编译掉的代码算作执行不到。平台和工具链才是固定环境。

**为什么**
- 这是对数据集动态标注依据的**静态化**。标注理由和覆盖记录表明，标注者判断的是“这次变更的核心是否被 harness 触达”，而不是“改动的每一行是否都被覆盖”。
- 所有阳性样本的修复，都是改变 harness **使用同一个操作的方式**（分段调用、重复初始化、打开编译开关、多传一个选项、修正判反的检查、删掉重复调用），没有一条是“去调用一个全新的入口”。
- 把构建配方当作目标的一部分，与 D2 的原则一致：不能用 harness 当前的设置来界定范围，因为这些设置本身可能已经过时。

**证据**
- 数据集中 11 条阴性的变更覆盖率小于 1（最低 0.042），说明“每一行都要被覆盖”的口径与标签不符。
- 改用两步法后，V3-19、V3-20、V3-22、V3-27、V3-41 从误报转为正确，V3-12、V3-16 被正确检出；两次全量的平均准确率从 75.0% 提升到 82.3%。

### P3 时间归因：按义务类别区分，覆盖类义务看“最内层从未被满足的条件”

**做法**（T2）
- **运行兼容类**：比较修改前后的失败情况。修改后失败、修改前不失败 → 本次引入；两侧以同样方式失败 → 原本存在。
- **覆盖类**：找出最内层那个在目标下从未被满足的条件，即真正挡住执行的判断，可能在源码、预处理指令或 harness 中：
  - 这个条件是本次新增的 → 本次引入；
  - 修改前就存在、并且同样从未被满足 → 原本存在，即使它后面新加了代码；
  - 修改前存在且能被满足、是本次修改让它无法满足 → 本次引入（退化型）。

**为什么**
- 两种直觉判法都有反例：“看阻碍是否原本存在”会判错 V3-16（新增行为被旧的单次调用挡住，真值是本次引入）；“看代码是否新增”会判错 V3-12（新代码位于原本就被编译掉的块里，真值是原本存在）。
- “最内层从未被满足的条件”能同时解释这两种情况，也与数据集的定义一致：把修复应用到修改前的版本上，看同一个缺口是否随之消失。

**证据**：V3-16、V3-12、V3-44、V3-10 全部判对；两次全量的时间判断正确数从 14/24 提升到 17–19/24。

## 第二层：判断方法

### P4 规格驱动：规格是提示词的唯一来源

**做法**
- 判定规则写成带编号的条款（定义 D、维护判定 J、时间判定 T、证据 E），提示词由 `spec.render(条款编号...)` 自动生成，每句话都能追溯到一条条款。
- 对旧提示词逐句审计：只针对个别样本的规则删除；背后有一般原则的，改写成条款。
- 每一次修订都记录动机、依据，以及是否在看过开发集之后做出（`docs/规则审计.md`）。
- 用测试来保证已删除的措辞不再出现、引用的条款编号都存在。

**为什么**
- 基于大模型的方法，最大的风险是**在开发集上“调”出来的效果**。规格驱动可以保证：每个判断都能追溯到定义，每条定义都能单独消融，方法的泛化能力可以被审查。

**证据**
- 删掉 19 条针对样本的规则后，召回率一度从 96% 降到 67%，说明 v7 的高召回很大程度上依赖这些规则；
- 之后只靠有原则的定义修订（P2、P3），召回率恢复到 79.2%，而误报率比 v7 低了一半以上。

### P5 模型提出，程序核验与汇总

**做法**
- 模型只给出语义判断和**引用的位置**（单元 ID 和行号）；引用的原文由程序按内容哈希取出并核验，引用还必须落在正确的一侧（修改前 / 修改后 / harness）。
- 五项前提是否齐全，由程序检查（必要性闸门）。
- 阴性要由程序确认所有变更组和四项基础都已闭合。
- 时间标签由程序根据两侧的事实推导；时间轮不能改变复核轮确定的必要性。
- 引用修复轮只能替换被指出的引用位置，判断和理由一律冻结。

**为什么**
- 模型擅长理解代码语义，但并不可靠：会写错行号，会前后矛盾，会给出没有证据的结论。把“证据是否真实、结论是否由证据推出”交给程序，模型出错时就落到 `unknown`，而不会变成看似有把握的错误结论。结论因此也可以审计。

**证据**
- 越界的引用被核验拦下，并由修复轮修正；
- 时间轮曾把已确认的义务判成“不必要”，冻结必要性之后就不再推出“无缺口”；
- 某一轮被安全过滤拦截时，该样本记为 `unknown`，而不是错误结论。

### P6 不对称的三值判定

**做法**（J3、J4、J5）
- 判阳只需要**一条**已证的义务；
- 判阴需要**所有**变更组和四项基础都有肯定性的证据；
- 证据不足时输出 `unknown`，缺少证据永远不能当作“没有缺口”。

**为什么**
- 在 PR / 合并检查的场景里，误报会损害开发者对工具的信任，而漏报至少不会给出错误的保证。三值输出让工具可以说“不确定，请人工看一下”，比强行二选一更诚实，评测时也能单独披露。

## 第三层：工程落地

### P7 模型找不到的证据，由程序确定性地补齐

**做法**
- **编译期配置**：变更外层的预处理条件、条件中出现的宏在仓库中的定义位置、构建配方里的配置开关（包括构建配方调用的源码树脚本）。
- **构建路径**：构建配方引用的每个仓库路径是否存在；对缺失的路径，给出第一个缺失的组件和同名目录出现在哪里。
- **构建上下文**：harness 侧的 Dockerfile（工作目录、文件复制位置）和仓库根目录的 Makefile。
- **时间判断的前后配对**：义务引用到、但本次没有改动的文件，也发送修改前后的版本，并标记为两侧相同。
- 这些事实只作为导航；对应的原始行同时加入证据，供模型引用。

**为什么**
- 模型的推理能力不是瓶颈，**看不到关键证据才是**。按函数名检索拿不到宏、构建路径、文档注释这类不依附于符号的证据，而它们可以由程序精确地提取出来，不需要模型去猜。

**证据**
- V3-03（构建路径失效）、V3-12（功能被编译掉）原本漏报，补上证据后检出；
- V3-22、V3-29 原本因证据不全落成 `unknown`，补上后正确判阴；
- 时间轮补发前后配对后，V3-03、V3-04、V3-08 的时间判断全部转为正确。

**反面教训**：V3-17 漏报，是因为 harness 调用的函数只读前 16 个，关键函数 `png_start_read_image` 被截掉了。证据覆盖的缺口，会直接变成判断错误。

### P8 一条样本一个会话、只发增量、保持缓存稳定

**做法**
- 证据包只构建一次，维护判断和时间判断共用；
- 级联：发现 → 复核 → 按需进行新候选复核、引用修复、补读后复核 → 只在报警时进行时间判断；
- 后续轮次只发送新增的证据；
- 所有轮次共用一个“对象或 null”的输出 schema；
- 后端支持时，复核轮从发现轮分叉出来。

**为什么**
- 实测表明，耗时几乎完全由**输出 token 和调用轮次**决定：单次调用的耗时与输出 token 的相关系数为 0.96，与输入 token 无关。所以要减少轮次、避免重复工作。
- 输出 schema 被放在提示前缀里，schema 不变，缓存才能持续命中。“对象或 null”的写法从格式上杜绝了“一段返回多项”的错误。

**证据**
- 单条样本从 1686 秒降到 371 秒，调用从约 21 次降到 3.3 次，输入 token 的中位数降为原来的约 1/5；
- 每轮换 schema 时，续接的缓存命中变成 0；
- 改用“对象或 null”后，项数错误从约 4% 降到 0。

**反面教训**：只在提示词里限制字数，没有带来稳定的压缩（4 条样本的总耗时只降了 2.5%）。压缩的重点应该放在**减少轮次**，而不是让模型写短一点。

## 第四层：评测方法

### P9 让静态定义与动态标注的口径对齐

**做法**
- 先读懂数据集的操作定义：阴性看构建、回放崩溃和变更覆盖；隐式阳性看缺口行修复前后的覆盖；显式阳性看构建失败或回放崩溃。再让规格的判据与之对应。
- 明确列出无法对齐之处：静态判断看“可能执行到”，动态实测看“在预算内实际执行到”；harness 中从未被触发过的缺陷，静态推理会计入，回放则看不到。

**为什么**
- 指标的高低首先取决于**口径是否一致**。最初大量的误报并不是模型能力不足，而是定义与标签不一致。在论文里，这些口径差异本身就是需要报告的结论。

### P10 重复运行，并把技术失败单独统计

**做法**
- 每个配置至少跑两次，报告平均值和两次之间的一致性（维护结论一致、是否报警一致、时间结论一致）；
- 网络、额度、安全过滤这类技术失败单独归类，不计入方法本身的错误；
- 额度耗尽时，整批运行作废，不把失败写成结果。

**为什么**
- 在完全相同的输入下，模型的输出也会不同；由模型驱动的补读还会放大差异。只跑一次，无法区分“改动真的有效”和“这次运气好”。

**证据**
- 结论翻转的 9 条样本中，有 7 条第一轮的输入完全相同；
- 最新规格下两次全量之间，是否报警一致 41/48；
- 曾有一次全量因额度耗尽而作废（task1）。

### P11 开发集纪律与修订日志

**做法**：每次修订都记录动机、依据，以及是否在看过开发集之后做出；最终结论必须在**冻结规格之后**，用独立的测试集来验证。

**为什么**：这是基于大模型的方法最容易被质疑的地方。修订日志把“调参”变成透明、可复核的方法演进过程。

## 尚不成熟的部分

1. **“核心行为”的认定**仍依赖模型的语义判断。例如 V3-37 中，模型把新增上限的“拒绝分支”当成了核心，需要更明确的判据，或者让模型给出可核验的定位。
2. **“harness 自身的操作在所有输入上都无法真正执行”这类情况**（V3-11、V3-10、V3-17）还没有纳入规格，规格的完整性还有缺口。
3. **证据覆盖的完整性**，例如检索上限、API 文档注释，直接影响结果，目前没有系统性的度量。
4. **静态可达性误判**，例如 V3-36，仍然存在。
5. 以上所有指标都来自开发集；多处规格修订是在看过开发集之后做的。
